# Stage 01 of 16 — Establish the upgrade test baseline

Read `docs/README.md` in full before changing anything. This stage starts the upgrade sequence and exists to lock the roadmap into executable tests. Inspect the repository, current test infrastructure, and `git status`; preserve all unrelated work already present. Work on the implementation, not merely a written plan.

Create or reorganize test support so the roadmap can be implemented safely against PostgreSQL and the ASP.NET Core application. Add compile-safe, clearly named tests for the Phase 0 requirements: generated license-ID format and concurrent uniqueness/monotonicity; activation-code alphabet, format, hashing, and one-time disclosure; mandatory normalized customer email and `metadata.contactEmail`; controlled product, edition, and license-type values; one entitlement per portal/API-issued license; expiry rules and signed entitlement expiry; cancellation rules; expiry amendments into the past; revocation/deactivation confirmation posting; authorization; and the online/offline invalidation boundary.

Use tests at the lowest useful level and shared fixtures/builders to avoid a single enormous end-to-end class. Prefer real PostgreSQL for database constraints, transaction isolation, and concurrency behavior. Keep secret assertions negative: verify that plaintext credentials are absent from persisted rows, audit context, logs, exceptions, and later GET responses. Do not weaken existing activation, transfer, signing, Identity, MFA, or passkey coverage.

This is an intentional red-test stage for behavior that does not exist yet, but the solution and tests must compile. Separate the results of the pre-existing baseline from the new roadmap tests so failures are attributable. If a proposed surface cannot be referenced without inventing production types, express it through public HTTP behavior or a narrowly scoped test contract; do not add fake production implementations merely to make tests compile. Document the expected red tests in the test source or a small test README, with the later stage expected to make each green. Do not skip or disable tests simply because they fail.

Run the existing baseline tests first, then the new targeted tests, and record exact commands and results. Finish by reporting the test files/support added, baseline regressions (which must be fixed if caused by this stage), the intentional failures grouped by later stage, and any genuine blocker. Do not implement the roadmap features in this stage.
