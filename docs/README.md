# License administration roadmap

Status: implementation plan for the current proof of concept  
Last updated: 2026-08-13

This document turns the requested licensing workflows into an implementation plan for this repository. It is intentionally specific about database invariants, API behavior, permissions, and testable outcomes.

## Non-negotiable requirements

- A license ID is generated by the application and allocated atomically by PostgreSQL. Operators and API clients cannot supply or change it.
- The public form of an ID is `LIC-YYYY-MMDDXXXXXX`, where each `X` is an uppercase hexadecimal character (`A-F` or `0-9`). Example: `LIC-2026-081300002A`.
- An activation code is generated with a cryptographically secure random-number generator, is read-only, can be copied, is returned only once, and is stored only as a hash.
- The activation-code form is `XXXXXXXX-XXXX-XXXX-XXXX-XXXXXXXXXXXX` and uses uppercase, unambiguous characters only.
- The administration UI and API issue one product per license record. The signed-license schema may remain capable of containing multiple entitlements for a future support CLI, but the portal does not create multi-product records.
- Products come from an administratively managed catalog; they are not free text.
- Edition and license type are controlled values and are validated in both UI and server code.
- Subscription and evaluation licenses require an expiry. Perpetual licenses use the canonical expiry `9999-12-31T23:59:59.999999Z` and are presented as `Never (perpetual)` in the UI.
- An unactivated license can be cancelled. An activated license can be revoked. Authorized operators can move an expiry into the past, with an audit entry and an explicit warning.
- Every customer has a valid email address.
- **Every newly issued license MUST contain the normalized customer email in license metadata as `metadata.contactEmail`. Issuance must fail if it cannot be written there.** This applies equally to the UI, API, automation, seed data, and later Stripe flows.
- Administrative actions are available through a versioned API with scoped bearer credentials, not only through the browser UI.
- Every sensitive mutation is authorized on the server and recorded in the append-only audit trail.

## Current repository assessment

The current application already provides PostgreSQL persistence, ASP.NET Core Identity, an `Administrator` policy, audit records, activation/deactivation/refresh, revocation, and signed license generation. It also hashes activation codes and activation tokens at rest.

The following gaps explain the reported behavior and define the work ahead:

| Area | Current state | Required change |
| --- | --- | --- |

## Domain and database changes

### License identifiers

Add a `LicenseIdCounter` table:

| Column | Type | Rule |
| --- | --- | --- |
| `BusinessDate` | `date` | Primary key |
| `LastValue` | `integer` | Range `0..16777215` |

Allocation occurs inside the same database transaction as license creation:

1. Resolve the business date using configurable `Licensing:IdTimeZone` (default `Australia/Adelaide`). Continue storing all actual timestamps in UTC.
2. Atomically upsert the date row and increment `LastValue` using `INSERT ... ON CONFLICT ... DO UPDATE ... RETURNING`.
3. Format the returned value as six-character uppercase hex.
4. Produce `LIC-{yyyy}-{MMdd}{value:X6}`.
5. Keep the unique index on `Licenses.LicenseId` as a final integrity boundary.
6. Fail clearly if daily issuance exceeds `0xFFFFFF`; never wrap or retry with random data.

This produces chronological IDs within a business day while satisfying the requested character set. Allocation belongs in a dedicated service and cannot be overridden by UI or API model binding. `LicenseId` remains immutable after insertion.

### Activation codes

Use the alphabet `ABCDEFGHJKMNPQRSTUVWXYZ23456789`. It excludes `0`, `O`, `1`, `I`, and `L`, covering the ambiguous characters listed in the requirement after conversion to uppercase.

Generate 32 characters with `RandomNumberGenerator.GetInt32`, then format them as `8-4-4-4-12`. Do not use GUIDs, `Random`, timestamps, counters, or modulo-reduced random bytes.

The create service, not the browser, generates the code. The service returns an issuance result containing the plaintext exactly once and stores only a versioned password hash. The current SHA-256 comparison can be retained for compatibility, but the preferred new format is an HMAC-SHA-256 lookup hash using a server-side pepper, with a hash-version column to permit future rotation.

The create page displays the result in a read-only field and provides `Copy activation code`. It must also state that the code cannot be recovered. Navigating away removes it from UI state. It must never appear in logs, audit context, URLs, analytics, exception messages, email unless explicitly sent through an approved issuance template, or subsequent GET responses.

API creation returns the activation code once in the `201 Created` response. Retries use an `Idempotency-Key`; the encrypted one-time result should be retained only for a short, defined retry window so a network retry does not accidentally issue a second license. After that window, the code is not recoverable and rotation is a separate audited action.

### Customers and mandatory email metadata

Extend `Customer` with:

- `Email`: normalized display value, required;
- `NormalizedEmail`: required and indexed for case-insensitive exact lookup;
- optional future billing fields such as `StripeCustomerId`, kept outside signed metadata.

Change `LicenseRecord.MetadataJson` from a text column to PostgreSQL `jsonb`. At creation, the domain service constructs metadata itself and always writes:

```json
{
  "contactEmail": "customer@example.com"
}
```

`contactEmail` is a required, normalized email string and follows the existing lower-camel-case metadata contract. Other approved scalar metadata can coexist with it. Clients may propose metadata but cannot remove, null, overwrite with a different email, or nest `contactEmail`; the service writes the authoritative value after validating the customer.

Because email is required in signed plaintext metadata, the UI must explain that it will be visible to anyone holding the signed license. Do not place secrets, payment data, API keys, or Stripe objects in metadata.

Search should use `Customer.NormalizedEmail` for performance and may also expose a JSONB expression index on `MetadataJson ->> 'contactEmail'` as a database integrity/search aid. Add a check constraint or save interceptor that rejects a license whose metadata lacks a valid `contactEmail`. Application validation alone is insufficient for this requirement.

When a customer's email changes, keep two concepts clear:

- `Customer.Email` is the current contact and search address.
- `metadata.contactEmail` is the immutable issuance snapshot for that license version. An explicit reissue/update operation may replace the snapshot, increment the license version, and audit old/new values.

### Product catalog

Add `ProductDefinition`:

| Column | Rule |
| --- | --- |
| `Id` | Internal UUID primary key |
| `Code` | Required lower-case stable identifier, unique, immutable after first use |
| `DisplayName` | Required operator-facing name |
| `Description` | Optional |
| `IsActive` | Controls whether it appears during issuance |
| `CreatedAt`, `UpdatedAt` | UTC audit timestamps |

Use `/products` as the management page. Authorized product administrators can add, rename, activate, and archive products. “Remove” means archive (`IsActive = false`) once referenced; historical licenses must never be broken by deleting a product row. A never-referenced product may be hard-deleted only if there is a strong reason, but soft deletion everywhere is simpler and preferred.

`Entitlement` should reference `ProductDefinition.Id` while retaining the immutable product-code snapshot used in signed artifacts. The issuance page lists active products in a dropdown and posts the product ID. The server resolves the code; it never trusts a posted code/display name.

The administration issuance service enforces exactly one entitlement. Keep the core signed schema's entitlement array so a future support CLI can aggregate products without changing every product validator. Design of that aggregation CLI—including activation semantics across multiple source license IDs—is a separate deliverable.

### Editions and license types

Create one shared set of domain values used by UI, API validation, database constraints, and tests.

Initial editions, exactly as lower-case codes:

- `community`
- `project`
- `education`
- `consumer`
- `business`
- `smb`
- `enterprise`
- `corporate`

The create UI uses a dropdown. Requests containing other values receive `400 Bad Request` with field-level validation details. If more editions are needed later, add them intentionally through a migration or a separately authorized edition catalog; do not fall back to free text.

License types are exactly:

- `perpetual`
- `subscription`
- `evaluation`

Expiry rules:

| Type | Create rule | Stored/signed expiry |
| --- | --- | --- |
| Perpetual | Expiry input hidden/disabled | `9999-12-31T23:59:59.999999Z` |
| Subscription | Expiry required and initially in the future | Operator-supplied UTC instant |
| Evaluation | Expiry required and initially in the future | Operator-supplied UTC instant |

The signed entitlement must include `expiresAt` for all three types so server state and product validation agree. The UI renders the perpetual sentinel as “Never,” not as year 9999.

### Lifecycle state

Add explicit cancellation fields to `LicenseRecord`:

- `CancelledAt`;
- `CancellationReason`;
- `CancelledBy` or an actor reference where appropriate.

Keep revocation fields separate. Derive display state using this precedence:

1. `cancelled`
2. `revoked`
3. `expired`
4. `active`
5. `available`

Rules:

- **Cancel** is allowed only before any activation has ever been created. It is terminal, requires a reason and explicit confirmation, blocks future activation, and records `license.cancelled`.
- **Revoke** is allowed for any non-cancelled license, is terminal, requires a reason and explicit confirmation, blocks activation/validation/refresh, and records `license.revoked`.
- **Expire now / change expiry** is an audited terms amendment. Authorized users may set the expiry to any explicit instant, including yesterday. A past value immediately makes server-side activation, validation, and refresh fail. Record old value, new value, reason, actor, and license version.
- A cancelled or revoked record is retained. No normal UI/API action deletes licenses or audit history.
- Previously issued offline files cannot be recalled or changed. Every lifecycle screen and API description must repeat this limitation. Online checks observe the new state immediately; downloaded artifacts observe changes only after a refreshed/reissued signed file.

The current revoke/deactivate controls must be repaired as part of the first implementation phase. Checkbox state needs an interactive render mode (or a submit button that is not permanently disabled), but the checkbox is only a usability guard. The handler/API must independently require confirmation, reason, authorization, antiforgery for cookie requests, and a concurrency/version check.

## Administration user experience

### `/licenses/create`

The form contains:

- read-only “Generated on issue” License ID placeholder;
- required customer/company name;
- required customer email;
- active product dropdown;
- edition dropdown;
- license type dropdown;
- conditional expiry date/time for subscription/evaluation;
- seats;
- optional updates-until date;
- approved additional metadata fields.

It does not accept a license ID or activation code. After successful issuance, stay on an issuance-result screen long enough to show:

- allocated License ID;
- read-only activation code;
- Copy button with accessible success/failure feedback;
- a warning that the code is shown once;
- link to the new license detail page.

Disable double submission, use an idempotency token, and do not show a success result until the transaction containing customer, metadata, product entitlement, ID allocation, activation-code hash, and audit event commits.

### `/licenses/{licenseId}`

Add separate, permission-gated panels:

- Edit license terms: expiry, seats, updates-until, and controlled edition;
- Cancel license: shown for licenses with no activation history;
- Revoke license: shown for issued/activated licenses;
- Activation/deactivation controls;
- immutable history with old/new values;
- customer name and email, with a clear label that email is present in signed metadata.

The red action button must respond when confirmation is checked. Inline validation must explain a missing/short reason rather than silently leaving the button unusable. On success, refresh status immediately and prevent repeated mutation. On stale `Version`, show a conflict message and reload current state.

### `/products`

Provide list, search, add, edit display name/description, activate, and archive. Show how many licenses reference each product and prevent code changes after first use.

### `/settings/users`

Provide invite/create, disable/enable, role assignment, permission inspection, MFA status, forced password reset, and API-credential ownership. Do not expose password hashes, authenticator secrets, recovery codes, or passkey material.

### `/settings/api-keys`

Provide create, one-time reveal/copy, name, owner/service account, scopes, created/last-used/expiry timestamps, rotate, and revoke. Never display stored token hashes or allow an expired/revoked credential to be restored.

## API plan

### Current API boundary

The repository currently exposes anonymous device endpoints for activate, validate, refresh, and deactivate. Administrative API coverage is limited to cookie-authenticated `GET /api/v1/admin/licenses/{licenseId}` and `POST /api/v1/admin/licenses/{licenseId}/revoke`. There is no API-key/token management section today.

### Authentication

Keep browser administration on secure Identity cookies with antiforgery protection. Add bearer authentication for automation:

```http
Authorization: Bearer lic_live_<public-id>_<secret>
```

Use a recognizable non-secret prefix/public ID for lookup and at least 256 bits of random secret material. Store only a versioned HMAC/hash of the secret, plus prefix, last four characters, owner, scopes, expiry, created/last-used/revoked timestamps. Show the full value once.

Bearer requests do not use antiforgery tokens because credentials are sent explicitly in the `Authorization` header. Cookie-authenticated API mutations continue to require antiforgery. Require HTTPS outside development, redact authorization headers, rate-limit by principal and IP, support immediate revocation, and make key expiry mandatory for human-owned keys. Production automation should use service accounts rather than a person's permanent key.

### Permission scopes

Use named permissions rather than one all-powerful role:

- `licenses.read`
- `licenses.issue`
- `licenses.update`
- `licenses.cancel`
- `licenses.revoke`
- `activations.manage`
- `customers.read`
- `customers.manage`
- `products.read`
- `products.manage`
- `users.read`
- `users.manage`
- `apiKeys.manageSelf`
- `apiKeys.manageAll`
- `audit.read`
- `billing.manage`

The same ASP.NET Core authorization policies protect pages, handlers, and API endpoints. Hiding a navigation item is not authorization.

Suggested built-in roles:

| Role | Intended permissions |
| --- | --- |
| System Administrator | All permissions and security configuration |
| License Manager | Full license/customer/activation lifecycle, audit read |
| License Issuer | Read and issue; no cancel/revoke/user management |
| Support Agent | Read plus activation/deactivation support |
| Product Administrator | Product catalog management |
| Auditor | Read-only licenses, customers, users, and audit |
| Billing Automation | Narrow issue/renew/customer scopes for Stripe processing |

Seed these roles and claims idempotently. The existing `Administrator` role can map to System Administrator during migration.

### Administrative endpoints

Proposed `/api/v1/admin` surface:

| Method and route | Purpose | Permission |
| --- | --- | --- |
| `GET /licenses` | Page/filter by ID, customer, email, product, status | `licenses.read` |
| `POST /licenses` | Issue one product license; returns ID/code once | `licenses.issue` |
| `GET /licenses/{licenseId}` | Full administrative detail | `licenses.read` |
| `PATCH /licenses/{licenseId}/terms` | Amend expiry/edition/seats/update coverage | `licenses.update` |
| `POST /licenses/{licenseId}/cancel` | Cancel never-activated license | `licenses.cancel` |
| `POST /licenses/{licenseId}/revoke` | Revoke license | `licenses.revoke` |
| `POST /licenses/{licenseId}/activation-code/rotate` | Invalidate and issue a new code once | `licenses.update` |
| `POST /activations/{activationId}/deactivate` | Operator-assisted deactivation | `activations.manage` |
| `GET /products` | List product catalog | `products.read` |
| `POST /products` | Add product | `products.manage` |
| `PATCH /products/{id}` | Edit/archive/activate | `products.manage` |
| `GET /customers` | Search customers including normalized email | `customers.read` |
| `PATCH /customers/{id}` | Update current customer contact details | `customers.manage` |
| `GET /users` | List operators/service accounts | `users.read` |
| `POST /users` | Invite/create operator | `users.manage` |
| `PATCH /users/{id}` | Disable or change roles | `users.manage` |
| `GET /audit` | Filtered append-only audit | `audit.read` |

Use `application/problem+json` consistently. Publish OpenAPI with request/response examples and documented security schemes. Support pagination limits, stable sorting, correlation IDs, `Idempotency-Key` for create/integration mutations, and `ETag`/`If-Match` or explicit `version` for updates.

Device-facing activation endpoints remain separate from administrative bearer scopes. They continue to use the license activation code plus client-generated activation token and must receive stricter rate limits to resist credential guessing.

## Operator identity and access control

Identity already supports passwords, TOTP, recovery codes, and passkeys. Extend it rather than creating a second user store.

Implementation rules:

- Only `users.manage` can create/invite, disable, or grant roles.
- Prevent an administrator from removing the final enabled System Administrator.
- A disabled user loses cookie sessions and bearer credentials promptly by updating the security stamp and revoking owned keys.
- High-risk permissions (`users.manage`, `apiKeys.manageAll`, `licenses.revoke`) require MFA in production.
- Prefer invitation links and forced password setup instead of an administrator choosing another user's reusable password.
- Audit login security events, invitations, role changes, key creation/rotation/revocation, and user disablement without recording secrets.
- Apply permissions at action level. A user allowed to view a screen may not automatically issue, update, cancel, or revoke.

## Customer access without a password

Do **not** use License ID plus Activation Code as a reusable customer-portal login. The activation code is a product activation credential; reusing it for portal sessions increases exposure, encourages storage in browsers/password managers, and gives anyone who sees a license email ongoing access.

Use a passwordless email flow:

1. Customer enters license ID and email, or only email.
2. Always return the same generic response to prevent account/license discovery.
3. If the normalized email matches the customer/license record, send a single-use magic link or email OTP through MailerSend.
4. Token is hashed at rest, expires in 10-15 minutes, is single-use, rate-limited, and creates a short customer session restricted to that customer's records.
5. Sensitive actions such as deactivation, contact-email change, or invoice access require a fresh email challenge.

Initial customer portal scope should be read-only license status, product/edition/seats, expiry, activation status with redacted device suffix, and invoice/renewal links. Add self-service deactivation or renewal only after abuse controls and Stripe ownership mapping are complete. Never reveal activation-code plaintext because it is not stored.

## Stripe integration plan

Stripe is a later phase, but the domain boundaries should be prepared now.

Add an anonymous transport endpoint such as `POST /api/v1/integrations/stripe/webhook` with these constraints:

- Read the untouched raw request body and verify Stripe's signature using the endpoint secret before parsing or doing work.
- Store Stripe event ID in a unique `WebhookInbox` row before processing. Duplicate deliveries return success without repeating side effects.
- Acknowledge quickly; process through a durable background worker/inbox-outbox flow.
- Store secrets in environment/orchestrator secrets, never appsettings committed to source.
- Map Stripe customer/subscription/price/product IDs to internal customer, product, contract, and license records using dedicated columns/tables—not signed metadata.
- Treat webhook order as non-deterministic. Fetch current Stripe object state when an event alone is insufficient.
- Audit business actions with Stripe event ID and internal IDs, excluding payment details and secrets.

Candidate events include completed checkout, successful/failed invoice payment, subscription created/updated/deleted, and refund/dispute events. Exact event-to-license policy must be configured rather than assumed:

- successful initial payment: issue or activate entitlement;
- successful renewal: extend subscription expiry idempotently;
- payment failure: notify and enter a configurable grace period, not immediate destructive revocation;
- cancellation at period end: preserve access through paid-through date;
- refund/dispute: flag for policy-driven review or suspension.

Use an internal `BillingContract`/`LicenseOrder` model so Stripe is an adapter, not the owner of licensing rules. This also leaves room for invoices, purchase orders, and other payment providers.

## MailerSend integration plan

Replace the no-op Identity sender with provider-neutral services:

- `ITransactionalEmailSender` for sending;
- `EmailOutbox` for durable queued messages;
- provider adapter for MailerSend;
- template mapping/versioning for purchase, activation delivery, renewal reminder, renewal receipt, payment failure, invoice, user invitation, email confirmation, and customer magic link;
- provider message ID, attempt count, next-attempt time, and final status for operational visibility.

Commit the business transaction and outbox row together, then send asynchronously with bounded retries and exponential backoff. Use idempotency keys so a worker retry does not send duplicates. Configure sender domain/API token outside source control. Add a MailerSend webhook later for delivery, bounce, and complaint updates; verify its authenticity and deduplicate events.

Email addresses and message content are personal data. Redact logs, enforce retention, and do not copy full message bodies into audit records.

## Test and acceptance checklist

### Issuance

- [ ] A user/API client cannot provide or overwrite a License ID.
- [ ] 1,000 concurrent creations produce unique IDs matching `^LIC-[0-9]{4}-[0-9]{4}[A-F0-9]{6}$` and daily hex values are monotonic.
- [ ] Activation codes match the requested segment lengths and never contain `0`, `O`, `1`, `I`, or `L`.
- [ ] Plaintext activation code is visible only in the successful issuance response and Copy works with accessible feedback.
- [ ] Database, logs, exceptions, audit, and subsequent APIs contain no plaintext activation code.
- [ ] Product and edition cannot bypass their catalogs with a forged POST/API request.
- [ ] Each portal/API-issued license has exactly one entitlement.
- [ ] Subscription/evaluation cannot be created without a future expiry.
- [ ] Perpetual stores/signs the canonical year-9999 expiry and UI displays `Never`.
- [ ] Signed entitlement expiry matches the server record.

### Mandatory metadata and search

- [ ] UI/API/Stripe issuance fails without a valid customer email.
- [ ] Every created license contains exactly one authoritative `metadata.contactEmail` normalized to the customer email.
- [ ] A client cannot omit or override `metadata.contactEmail` through custom metadata.
- [ ] Seeded/demo licenses also satisfy the email invariant.
- [ ] Searching by email returns the expected customer/licenses case-insensitively.

### Lifecycle

- [ ] Checking confirmation enables the red action and validation errors are visible.
- [ ] Never-activated license can be cancelled with a reason and can never activate afterward.
- [ ] License with activation history cannot use cancel and is directed to revoke.
- [ ] Authorized user can set expiry to yesterday; activation/validate/refresh then fail as expired.
- [ ] Revocation works before or after activation and is idempotent.
- [ ] Unauthorized users cannot update/cancel/revoke by direct HTTP calls.
- [ ] Every mutation records actor, timestamp, result, target, old/new non-secret values, and correlation ID.
- [ ] Offline limitation is visible and covered by tests.

### API and users

- [ ] API key is shown once, hashed at rest, scope-limited, expirable, rotatable, and immediately revocable.
- [ ] Missing/wrong scope returns `403`; missing/invalid token returns `401` without revealing lookup details.
- [ ] Cookie mutations require antiforgery; bearer mutations do not depend on cookies.
- [ ] Each built-in role passes allowed-action tests and fails disallowed-action tests.
- [ ] Disabling a user invalidates sessions and owned API keys.
- [ ] The final System Administrator cannot be removed or disabled accidentally.

### Integrations

- [ ] Mail is outbox-backed, retry-safe, redacted in logs, and observable by provider message ID.
- [ ] Customer magic links are hashed, short-lived, single-use, rate-limited, and customer-scoped.
- [ ] Stripe signature is verified against raw body before parsing.
- [ ] Duplicate/reordered Stripe events do not duplicate licenses, renewals, audit entries, or email.
- [ ] Payment failure uses the configured grace policy rather than silently revoking access.

## Definition of done

The work is complete only when UI and API use the same domain services and authorization policies; all issuance paths enforce product, edition, expiry, and mandatory email metadata invariants; secrets are never stored or logged in plaintext; lifecycle actions work reliably and are audited; clean PostgreSQL migration plus restart/seed is idempotent; and unit, integration, authorization, concurrency, and browser-level tests pass in the containerized environment.
